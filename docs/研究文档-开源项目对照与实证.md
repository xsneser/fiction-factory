# 研究文档：开源项目对照与实证——大纲 / 桥段 / 故事线 / 叙事线程

> 日期：2026-08-27　范围：**只读研究**，不涉及任何代码改动。
> 目的：为《故事线「大纲 / 桥段 / 线程」关系建模》§十「豆包对照与收敛模型」补充**外部开源实证**——验证真实开源项目如何定义这一部分，标出收敛主张里「有先例可引」与「差异化空白」的部分，为 §七 数据模型演进提供外部依据。
> 方法：三族 12 个开源项目调研（3 份外部报告）+ 主会话对关键源码的 `curl` 复核。置信度标注：`[主核验]` = 主会话直读源码/原文核对；`[调研源码]` = 调研 agent 直读源码；`[论文知识]` = 论文转述，未逐字复核；`[未逐字确认]` = 细节存疑，需复核。

## 一、结论先行

1. **收敛模型的两层拆法（内容素材层 vs 调度层）方向成立，有外部实证。** 没有哪个开源项目完全同构，但每一条主张都能在真实项目里找到对应物或清晰的空白。
2. **「纵向大纲树 × 横向剧情线」两轴分离是写作软件的成熟范式。** manuskript / novelibre / bibisco 三家中，novelibre 与 bibisco 显式把两条轴建成独立数据模型并互链；novelwriter 是反例（单树 + 文本内标题，丢失可查询的剧情线拓扑）。
3. **「一个最细单元同时属多条线（N-N 多归属）」有直接先例。** novelibre（`PlotlineNotes*` + `Sections ids=IDREFS` 双向关联，`dtd/novx_1_10.dtd`，已主核验）、bibisco（`scenestrands[]` 数组）。
4. **「大纲树多级嵌套」在 AI 长故事生成研究里有先例。** DOC（`detailed outliner creates a more detailed, hierarchically structured outline`，摘要已主核验）、DHO/LongStory（`storyline → chapter_outline → detail_outline` 层级，源码已主核验）。
5. **「大纲 = 目标节点」的类型切分（goal vs 可执行桥段）在公开研究里几乎无先例。** 主流是**粒度切分**（粗事件 → 细事件），Re3 / DOC / Outline2Story 的大纲节点都是「事件/要点陈述」而非「目标 + 字段」。最接近「目标 + 约束」的是 LongWriter 的「段落描述 + 目标字数」。这是收敛模型的**差异化主张**。
6. **「调度层 + 断点上下文」只有 ink 有完整物证。** `CallStack.Thread` 就是可序列化的断点快照（`ink-engine-runtime/CallStack.cs`，已主核验），`<- knot` 创建并行流程。Twine 是「纯素材图、零调度」的极端对照；Yarn Spinner / Ren'Py 只有单线 + 子程序调用栈。**AI 研究里没有任何一家有调度层概念**——这是收敛模型（也是本平台）可强调的空白亮点。

## 三、家族一：开源写作软件——两轴分离是成熟范式

| 维度 | manuskript | novelibre | novelwriter | bibisco |
|---|---|---|---|---|
| 纵向大纲树 | 独立 Outline 树（书→部→章→场景） | 独立 CHAPTERS（Novel→Part→Chapter→Section） | 文档树 + 正文 Markdown 标题（#~####=Part/Chapter/Scene/Section） | 独立 parts→chapters→scenes |
| 横向剧情线 | 独立 Plot 树（但只挂角色） | 独立 ARCS（=plot line）+ POINT | 仅 `@plot` 内联标签 + PLOT 类文档 | 独立 strands 集合 |
| 两轴是否独立模型 | **是**（但互相**无外键**） | **是**（显式互链，双向） | **否**（单树 + 标签） | **是**（显式互链） |
| 最细单元 | scene（Outline 的文本项） | Section | Scene/Section（文本标题行） | Scene |
| 线↔最细单元关联 | 无关联（只经角色间接对齐） | **N-N**（`PlotlineNotes*` + `Sections IDREFS`） | 松散 tag，无 FK | **N-N**（`scenestrands[]`） |
| 树状嵌套 | 大纲任意深度；plot 两层（plot→steps） | 纵向 4 层；ARCS 扁平 + 有序 POINT | 项目树任意深度；标题 4 级 | 纵向 3 层；strands 扁平 |
| 跨线视角 | 无 | **plot grid**（每 section × 每线备注） | Outline 视图（从标题/@tag 计算列） | analysis-strand-distribution |
| 持久化 | .msk（zip：MMD+OPML+XML） | .novx（XML+DTD，版本化） | nwProject.nwx（XML）+ content/*.nwd + meta/index.json | LokiJS JSON（每项目一库） |

### 3.1 novelibre——最干净的双轴 schema 范本（已主核验）

`dtd/novx_1_10.dtd` 顶层：`<!ELEMENT novx (PROJECT, CHAPTERS, CHARACTERS, LOCATIONS, ITEMS, ARCS, PROJECTNOTES, PROGRESS?)>`——**纵向 `CHAPTERS` 与横向 `ARCS` 并列独立**。

- **纵向**：`CHAPTER` 用 `level(1|2)` 属性区分 Part/Chapter（无独立 PART 元素），Section 挂 CHAPTER 下 → Novel→Part→Chapter→Section 四级。
- **横向**：`ARCS(ARC*)` **扁平列表、无嵌套**；每条 ARC 含 `ShortName`、`Sections ids=IDREFS`（指向多个 section）、有序 `POINT*`（每个 POINT 指向**单个** Section）。
- **N-N 双向关联**：SECTION 内可有**多个** `PlotlineNotes*`（每个 `id IDREF→ARC` 且自带独立注释文本），即「一个场景同时挂多条线，且每条线有独立备注」；ARC 侧反向 `Sections IDREFS` 持有场景 ID 列表。
- **最细单元自带微型戏剧结构**：SECTION 有 `Viewpoint(id IDREF)` + `Goal? / Conflict? / Outcome?`（各 `p*`）——与 §3.3 里「桥段 = 可执行片段」的意图一致，最细单元不仅存正文，还存目标/冲突/结果。

> 对收敛模型的映射：novelibre 已把「纵向大纲树」与「横向故事线」建成**两个独立模型并显式 N-N 互链**；缺的是「故事线拥有**自己的大纲树**」（novelibre 的 ARC 只有扁平 POINT，无子大纲）与「调度层」。

### 3.2 manuskript / bibisco / novelwriter

- **manuskript**：`Outline`（书→部→章→场景）与 `Plot` 是两个独立 `QStandardItemModel`（`manuskript/enums.py` 的 `Model` 枚举），plot 有 `importance(主/次/次要)`、`characters`、`steps`（子 plot）。**坑**：scene 与 plot 之间**没有外键**——Outline 枚举 19 个字段里无 plot 字段，Plot 也无 scene 字段，两者只通过「角色 ID」间接对齐。两轴分离但没连起来，是「半成品」先例。
- **bibisco**：`parts→chapters→scenes`（纵向）与独立 `strands`（横向叙事线索）集合；scene 的 revision 内 `scenestrands[]` 数组实现 N-N 多归属（同结构还有 `scenecharacters[]/sceneobjects[]`）；strands 扁平无嵌套；持久化为 LokiJS JSON（`<项目id>.json`，scene 带 `revisions[]` 版本化）。
- **novelwriter（反例）**：没有 outline/plot 的结构化二元模型——一棵统一文档树（`nwItemClass` 含 NOVEL/PLOT/CHARACTER/WORLD/TIMELINE 等根类），真正的 chapter/scene 粒度是**正文里 Markdown 标题行**（`#`~`####`），剧情归属靠内联 `@plot/@char/@pov/...` 标签 + `meta/index.json` 索引。Outline 视图是从标题和标签**计算**出来的。**警示**：只做「文本 + 标签」而非结构化图，就失去可查询的剧情线拓扑——正是我们 `thread_id` 方案若退化为纯文本会踩的坑。

## 四、家族二：交互叙事引擎——调度层只有 ink 真正实现

| 引擎 | 素材层（内容单元） | 流程/调度层 | 素材与调度分离？ | 显式线程/并行 | 挂起→切走→恢复断点 | 最小单元 | 可嵌套 |
|---|---|---|---|---|---|---|---|
| **ink** | `Container`（=knot/stitch）的 `content` 列表，含文本/Glue/Tag/**Divert**/**ChoicePoint**/**ControlCommand** | 运行时 `Flow → CallStack → [Thread...]` 栈（决定执行顺序、存断点） | **半分离**：控制对象内嵌在 content 流里，但调度器（Thread 栈）是独立运行时对象 | **是**（`CallStack.Thread` 列表 + `<- knot` 线程化跳转 + StartThread/Done 指令） | **是（最完整）**：`ForkThread()` 给 choice 快照线程，选中后 `currentThread = threadAtGeneration` 恢复 | 单个 `Runtime.Object` | **是**（Container 内嵌 stitch、weave 任意层级） |
| **Twine/Twee** | `passage`（name+tags+metadata+文本） | **无**（数据模型里没有；导航由故事格式 JS 运行时做） | **极端分离**：素材图里连链接对象都没有，链接是文本内 `[[...]]` 标记 | 否 | 否（是否保留返回栈由 JS 自行实现） | passage | 否（段落平坦） |
| **Yarn Spinner** | `Program → Node → Instruction`（字节码）+ Line 字符串表 | `VirtualMachine`（单 `State`：pc+值栈+options+callStack） | 编译后内容与控制合一（跳转/运行节点都是指令） | 否 | 部分（`CallSite` 栈是子程序返回，非并行） | Instruction / Line | 否（Node 扁平指令列表） |
| **Ren'Py** | script 文本：`label` + 语句（Say/Menu/Scene/If/While） | Python 解释器 + `Context.return_stack` | 不分离（剧本即代码） | 否（脚本 AST 无 parallel，`renpy/ast.py`） | 部分（`call` 压栈 `return` 弹栈；纯子程序） | 单条语句 | 部分（label 是扁平命名空间） |

### 4.1 ink——「线程 = 可序列化断点快照」的完整物证（已主核验）

`ink-engine-runtime/CallStack.cs`（已 curl 直读）核心：

```csharp
public class Thread {                       // 一个「执行线程」= 一次流程快照
    public List<Element> callstack;         // 栈帧列表（断点主体，Element 含 Pointer=container+index）
    public int threadIndex;                 // 线程编号
    public Pointer previousPointer;         // 序列化用的"上一位置"
}
List<Thread> _threads;                      // 线程栈（并行流程的集合）
public void PushThread();                   // 复制当前线程 → 新 threadIndex → 压栈（开新并行流程）
public Thread ForkThread();                 // 复制当前线程 → 返回（给 choice 存快照）
public void PopThread();                    // 结束当前线程，弹栈回到上一个
public Thread ThreadWithIndex(int index);
public Thread currentThread { get; set; }   // 当前执行线程（可整体替换 = 恢复断点）
```

- **静态素材**：`Container`（knot/stitch 基类）是一段可寻址内容块，`content` 列表里按序装文本对象 + 流程控制对象（`Divert` 跳转、`ControlCommand.StartThread/Done` 等）。
- **动态调度**：`Flow → CallStack → [Thread...] → [Element...] → Pointer(container, index)`，`CallStack` 就是「决定执行顺序 + 持断点」的调度器。
- **并行与断点恢复**：线程化跳转 `<- knot` 编译成「divert 到目标」+ 流里插一条 `StartThread`，运行时 `PushThread()` fork 出一条并行流程；choice 生成时 `ForkThread()` 给每个选项快照一份当前线程，玩家选中时 `currentThread = choice.threadAtGeneration` **整体恢复快照**——这就是「A 写一半挂起 → 切 B → 回 A 恢复断点」的原生实现。
- **weave/gather**：选项 `*` 分叉、gather `-` 收拢，任意层级嵌套（「an option is taken... finds the next gather down... options separate the paths, gathers bring them back together」，`Documentation/WritingWithInk.md`）。
- **nuance（重要）**：ink 的分离是「半分离」——`Divert`/`ControlCommand` 这类控制对象**物理内嵌**在 content 流里，只有**调度状态**（Thread 栈）是独立对象。这印证 §十 收敛模型的一个隐含前提：**素材与调度只需逻辑上可解耦（`thread_id` 语义重定位 + 独立调度器），不必物理隔离成两套对象**。

### 4.2 Twine / Yarn Spinner / Ren'Py

- **Twine/Twee**：`passage` 是 name+tags+metadata+单文本节点，链接就是文本内 `[[...]]` 标记，`startnode` 是唯一入口元数据——**数据模型里零调度**，下一步去哪全交给故事格式（Harlowe/SugarCube）的 JS 运行时。storylets（Harlowe `(storylet:)` 宏 / SugarCube 的 TinyQBN / StoryletManager）是在**素材图之上另建**的条件规则层，不入数据模型——佐证「调度独立于素材」这一主张。
- **Yarn Spinner**：`Program → Node → Instruction` 字节码，`VirtualMachine` 单 `State`，`callStack`（`CallSite{nodeName; instruction}`）只是子程序返回栈，无并行、无线程。
- **Ren'Py**：剧本即代码，`label/jump/call/return` 是脚本级控制；`renpy/ast.py` 全文件无 `parallel`（只存在于 ATL 动画语言）。

## 五、家族三：AI 长故事生成——「大纲=目标节点」几乎无先例，主流是粒度切分

| 项目 | outline 数据形态 | 粒度对应 (1 item = ?) | 区分「目标」vs「可执行事件」？ | 多级嵌套树？ |
|---|---|---|---|---|
| **Re3**（2210.06774） | `Plan`=扁平 `list[str]` 事件句；`Story Details`=逐项展开文本 | 1 plan item ≈ 1 段 | 是（粗=事件、细=对话动作），但无字段，是粒度差非类型差 | 否，仅 2 层 |
| **DOC**（2212.10077，已主核验摘要） | `detailed outliner creates a more detailed, hierarchically structured outline`；`detailed controller` 让段落对齐大纲 | 1 顶层点 ≈ 1 段；子点 ≈ 句 `[未逐字确认]` | 否，按粒度分 | **是**（层级大纲树） |
| **Outline to Story**（2101.00822，已主核验题名） | 两级级联事件：paragraph-level 事件 → 每段落事件再展开 sentence-level 事件 | 1 段事件=1 段；1 句事件=1 句 | 否，两级都是事件 | 否，仅 2 层 |
| **LongWriter**（2408.07055） | 层级大纲，段落级 item = {描述 + **目标字数**} | 1 段落 item ≈ 1 段（带字数预算） | 部分是（大纲=目标+预算、正文=落地），大纲无角色/事件字段 | 可多级（章/节/段） |
| **DHO/LongStory**（2412.13575，已主核验 README+源码） | `1storyline.py` 每故事生成 rough outline；`DOME.py` 主生成；`MEM.py` neo4j 知识图谱记忆；`DHO.py` 内 `storyline → chapter_outline → detail_outline` | 卷级→章级→段级 | 是（规划大纲 vs 状态记忆显式分离） | **是**（storyline→chapter→detail） |

> 备注：调研时「Ploutos（outline 作可控代理）」论文**未找到**——arXiv 上唯一同名是股票预测论文（2403.00782），无关；最吻合的真实论文是 **Outline to Story**（两级级联事件，编辑大纲句 = 细粒度控制代理）。

**空白点**：这 5 个研究项目全是**线性「大纲 → 正文」顺序展开**，没有任何一家有「调度层」概念——插叙/并行视角都要改大纲或素材本身，做不到「素材不动、只改调度」。收敛模型的调度主张在公开研究里是**空白**。

## 六、收敛模型逐条对照表（§十.2 每条主张 vs 开源实证）

| 收敛模型主张 | 开源先例 | 反例 / 空白 |
|---|---|---|
| **大纲 ≠ 卷**（卷是后处理分组） | DHO 有卷级（storyline）但作为大纲层，非纯后处理；novelibre 无卷概念（Part 是 CHAPTER `level=1`，是素材层分组） | **无直接先例**：写作软件把 Part/卷当素材层分组；AI 研究里卷级仍是大纲层。这是收敛模型对现状（book_002 大纲=卷）最激进、也最需要自家实现的修正 |
| **大纲 = 树状目标节点（可嵌套）** | DOC（层级大纲树）、DHO（storyline→chapter→detail） | Re3/Outline2Story 只有 2 层；公开研究的大纲节点是「事件句」非「目标+字段」 |
| **桥段 = 可执行剧情片段** | novelibre Section（自带 Goal/Conflict/Outcome + Content）、Re3 的 Story Details、Outline2Story 的 sentence-level 事件 | 研究里桥段粒度≈句子，写作软件里≈scene/section；与「约 0.3-2 章」的现有 PlotSlot 粒度存在尺度差 |
| **纵向大纲树 × 横向故事线 两轴分离** | novelibre（CHAPTERS ∥ ARCS）、bibisco（parts/chapters/scenes ∥ strands）、manuskript（Outline ∥ Plot） | novelwriter（单树+标签）——反例 |
| **故事线 = 因果链，拥有自己的大纲树 + 桥段池** | DHO `1storyline.py` 按故事线生成 rough outline；bibisco strands 是独立集合 | 无项目做到「每线一套大纲树」+「每线自带视角 POV」的完整形态；novelibre ARC 只有扁平 POINT |
| **一个桥段可属多条线（N-N 多归属）** | novelibre（`PlotlineNotes*`+`Sections IDREFS`）、bibisco（`scenestrands[]`） | manuskript 无外键（反例） |
| **叙事线程 = 调度器，决定输出顺序** | **ink**（`CallStack` 线程栈） | Twine 零调度（把调度推给 JS）；AI 研究全无此层 |
| **断点上下文（写一半挂起 → 恢复）** | **ink**（`Thread` 可序列化快照 + `ForkThread/currentThread=`） | Yarn/Ren'Py 只有子程序调用栈；AI 研究无此概念（以整桥段为单位、`written_chapter` 记进度是当前现状） |
| **素材不动、只改调度即可实现插叙/并行** | ink（weave/gather/divert 重排不改素材） | AI 研究线性展开，插叙需改素材 |
| **卷 = 纯后处理分组** | 无（见首行） | 全无先例——差异化主张 |

## 七、关键结论

1. **有实证、可直接引**：两轴分离（novelibre 最干净）、N-N 多归属（novelibre/bibisco）、大纲树嵌套（DOC/DHO）、调度层 + 断点快照（ink）。
2. **差异化空白点（收敛模型 / 本平台的竞争力所在）**：
   - **「大纲 = 目标节点」的类型切分**——公开研究都做粒度切分，没人做「目标 vs 可执行」的类型切分；
   - **「卷 = 纯后处理」**——所有写作软件/研究都把卷当素材层分组；
   - **「调度层 + 断点上下文」应用于 LLM 章节写作**——ink 有调度物证但那是交互叙事运行时，AI 生成侧无人做。
3. **需修正/注意的点**：
   - ink 是「控制指令内嵌素材流、调度状态独立」的**半分离**——收敛模型不必追求物理隔离，`thread_id` 语义重定位 + 独立调度器即可；
   - 现有 `thread_id` 一个桥段单归属 vs 开源 N-N 惯例（novelibre/bibisco 都支持一场景多线）——支持 §十.3「线程多归属」的收敛方向；
   - 桥段粒度：研究/写作软件最细单元（句子/scene）远细于现有 PlotSlot（0.3-2 章），收敛模型若把「桥段」定位为可执行片段，需明确与章节、场景的粒度换算。

## 十、术语表（增补）

| 术语 | 含义 | 出处 |
|---|---|---|
| 双轴分离 | 纵向大纲树（书/部/章/场景）与横向剧情线（plot/ARC/strand）建成两个独立数据模型并互链 | novelibre/bibisco/manuskript |
| N-N 多归属 | 一个最细单元（scene/section）同时属于多条剧情线，各线可带独立备注 | novelibre `PlotlineNotes*`、bibisco `scenestrands[]` |
| 断点快照 | 调度器为「执行到一半的单元」保存的位置+上下文对象，可序列化、可恢复 | ink `CallStack.Thread` |
| 粒度切分 | AI 研究主流：大纲按「粗事件 → 细事件」分层，不区分「目标 vs 可执行」类型 | Re3/DOC/Outline2Story |
| 类型切分 | 收敛模型主张：大纲=目标节点（要达成什么）、桥段=可执行片段（具体发生什么），是类型差非粒度差 | §十（差异化主张） |
| storylet | 带条件需求的叙事单元，运行时由规则层按可用性调度 | Harlowe/SugarCube 生态 |
