# 研究文档：故事线「大纲 / 桥段 / 线程」关系建模

> 日期：2026-08-25　范围：**只读研究**，不涉及任何代码改动。
> 目的：理清 大纲 / 桥段 / 线程 三者的关系，纠正「大纲 = 卷一/卷二」的现状，为后续数据模型演进提供依据。
> 依据：三份只读探索报告（数据模型 / 库与生成 / UI 与设计文档），结论均带 `file:line` 引用，可自行核对。

---

## 一、结论先行

1. **大纲 / 桥段 / 线程 是三个正交的维度，不是同义词，也不是层级递进。**
   - 大纲 = 情节弧（纵向切割，掌控故事走向，约 5–15 章）
   - 桥段 = 弧内的戏剧节拍（纵向粒度更细，约 0.3–2 章）
   - 线程 = 横向贯穿全书的一条叙事线索（主线/副线/伏笔线），由散布在不同弧里的桥段组成
2. **「大纲 = 卷」是错的。** 卷是比弧大得多的分组（20–100 章），大纲应是「末日来临前 10 章囤物资」这种粒度。
3. **你担心的插叙（A 桥段开头 → B 桥段再开头 → 分别收尾），代码已经支持**——就是「线程穿插排序 + 设局/收局」；真正缺的是**大纲粒度、线程可见性、UI 表达**，以及**并行视角（崩铁式）**这一全新能力。

## 二、概念模型：三个正交的维度

### 2.1 纵向粒度：大纲（情节弧）→ 桥段

一条故事的骨架是**嵌套的包含关系**（从粗到细）：

```
书 BookStoryline
 └─ 大纲（情节弧 Arc）      ← 掌控方向，约 5–15 章，有明确的戏剧目标/起承转合；可含子弧
     └─ 桥段（Plot Beat）  ← 执行内容，约 0.3–2 章，一个具体事件/场景；可含子桥段
```

- **大纲（情节弧）**：一段有方向感的叙事单元。它回答「这一大段要走向哪」。例：末日文「第 1-10 章：末日来临前疯狂囤物资」——目标是在期限前攒够资源，内部是「发现征兆 → 恐慌 → 抢购 → 冲突 → 惊险收官」的起承转合。
- **桥段**：落在弧内部、支撑弧目标的具体戏剧瞬间。例：囤物资弧里的「发现末日征兆 / 疯狂采购 / 与竞争者抢货 / 金手指变现 / 最后一批物资入仓」。
- **嵌套**：弧可以套子弧（一个大战役含多个小阶段），桥段可以套子桥段（一场战斗含几拍）。当前模型里**桥段套桥段已有字段**（`parent_plot_id`/`children_plot_ids`，`libraries/storyline.py:230-231`），但**弧套子弧没有**；弧内部的 `stages` 只是「卷内阶段」数据，不是一等公民。

### 2.2 横向贯穿：线程（Thread）

线程是**另一条轴**，与粒度无关：

- 一个桥段同时属于「一个大纲（纵向）」和「一个线程（横向）」。
- 一个线程由**跨多个弧**的桥段组成：如「伏笔线」可以在第 3 章（弧 1）设局、第 30 章（弧 3）收局。
- 现有线程约定：`主线 / 副线 / 伏笔阴谋线`（`libraries/outline_generator.py:1064-1073`），每个桥段一个 `thread_id`（`libraries/storyline.py:249`）。

**用户困惑解答**：「线程含义跟大纲桥段差不多？或者是中间一部分？」——都不是。线程是**横向贯穿的选择**，大纲/桥段是**纵向切割的粒度**。一根绳子（线程）穿过若干段竹竿（弧），每根竹竿里又有若干竹节（桥段）。用「绳穿过竹竿」这个图理解：竹竿段位 = 大纲，竹节 = 桥段，贯穿的绳 = 线程。

### 2.3 叙事手法 / 视角：第三条可选的轴

- **插叙/倒叙**：现有 `OutlineSlot.narrative`（`libraries/storyline.py:215-217`）= `chronological | flashback | interleaved`。**但只影响 UI 上色**（`ui/static/js/story_line.js:200-215`），**完全不进写作流程**（写作器/prompt_harness 无引用），`narrative_target` 存而不用（仅 `story_line.js:74` 一处读取）。
- **并行视角（崩铁式双线并排）**：当前**没有**。`basic_info.pov` 只是全局人称约束（默认第三人称），写作 prompt 明确「视角始终锁定主角，不切换」（`libraries/storyline_writer.py:37`）。这是未来扩展，不是现状能力。

## 三、你提的几个疑问，逐一解答

### 3.1 「A 桥段开头、B 桥段再开头、然后分别收尾」的插叙怎么表示？

**代码已经支持，机制是「线程穿插 + 设局/收局」两件事叠加：**

1. **线程穿插排序**：`_threaded_ordered_plots`（`libraries/storyline_writer.py:169-206`）把不同线程的桥段交错排列——主线每次取 2 个、其他线程各取 1 个，循环取完。`test_all.py:174` 的期望序列
   ```
   M1,M2,S1,V1,M3,M4,S2
   ```
   正是「A（主线）开头 → B（副线/伏笔）再开头 → 各自推进」的交错形态。
2. **设局→收局（分别收尾）**：`_apply_split_payoffs`（`libraries/outline_generator.py:1122-1160`）为「阴谋/悬疑/智斗/成长转折」类桥段生成跨阶段的**收局桥段**（`PlotSlot.resolves_plot_id`/`resolves_name`，`libraries/storyline.py:251-252`）。A 在第 2 章设局、B 在第 5 章设局、A 在第 12 章收局、B 在第 20 章收局——这就是「分别收尾」。

**结论**：插叙的**排序算法和设局收局机制都已落地**，写章节时也确实按穿插序逐桥段写（`storyline_writer.py:568-569`）。缺口在于：
- **UI 表达弱**：设局→收局之间没有连线（前端只有「↪ 收局」徽标，`story_line.js:333-338`），线程泳道也看不出「哪几个桥段构成一条线、哪处设局哪处收局」。
- **agent 生成时未必主动利用**：桥段库/生成 prompt 没有把「这条插叙线」当作一等概念来规划。

### 3.2 并行视角（崩铁式双线并排）怎么表示？

**当前模型没有，属于未来扩展。** 要做需要四件事（详见 §七）：
1. 桥段加 `pov` 字段（主角线/配角线/反派线…）；
2. 写作流程允许「同一时间窗内切视角」（现在 `storyline_writer.py:37` 明确锁定主角）；
3. UI 支持同时间窗双泳道并排（现在 `assignLanes` 只对时间重叠的**桥段**并排，`story_line.js:151-162`，没有 POV 概念）；
4. 写作 prompt 注入 POV 纪律。

### 3.3 大纲为什么不能是「卷」？

- 卷是**若干个弧的组合**（20-100 章，一个完整大篇章），而弧是**一个有方向的叙事段**（5-15 章）。「末日来临前囤物资」是弧不是卷——它是整个「末日篇」这个大卷里的一段。
- 用户直觉正确：把大纲当卷，故事线就只剩几个粗框，没有任何方向感与节奏可言；把大纲当弧，每 5-15 章就有一个明确目标，桥段才有用武之地。

## 四、现状映射：代码里已经有什么 / 缺什么

### 4.1 已有的能力（可直接复用）

| 能力 | 位置 | 说明 |
|---|---|---|
| 大纲→桥段包含 | `PlotSlot.outline_id`（`libraries/storyline.py:228`） | 桥段挂在大纲下；写作顺序 = `(outline 顺序, stage_index, order, thread_seq)`（`libraries/storyline_writer.py:178-180`） |
| 线程定义 | `主线/副线/伏笔阴谋线`（`libraries/outline_generator.py:1064-1073`） | LLM 可分配，英文 id 归一化，缺失兜底分类 |
| 线程穿插排序 | `_threaded_ordered_plots`（`libraries/storyline_writer.py:169-206`） | 主线 2:1 加权轮流取；全主线退化为严格顺序（`test_all.py:175-178`） |
| 设局→收局 | `_apply_split_payoffs`（`libraries/outline_generator.py:1122-1160`）+ `resolves_plot_id`（`libraries/storyline.py:251`） | 收局桥段天然落在线程后段，被其他线程穿插 |
| promises 台账 | `BookStoryline.promises`（`libraries/storyline.py:283-286`），写入 `engine.py:493-529`，扫描 `libraries/promise_ledger.py` | 设局 pending → 推进 advanced → 收局 fulfilled；前端桥段上 ⏳/✅ 徽标（`story_line.js:340-346`） |
| 桥段嵌套 | `parent_plot_id`/`children_plot_ids`（`libraries/storyline.py:230-231`），生成（`libraries/storyline.py:630-658`），前端层级+SVG 连线（`story_line.js:242-253, 358-389`） | **链式**嵌套（第 2、3 个桥段挂成前一个的子桥段）；但 **books/ 下没有任何真实嵌套数据**（全为 `parent_plot_id:""`） |
| narrative 视觉 | `story_line.js:200-215`（倒叙琥珀/插叙绿色）+ 图例 | **仅视觉**，不影响写作 |
| 线程 UI | 桥段圆点 + 线程横带 + 🧵 泳道（`story_line.js:328-332, 393-435`） | 线程有横带与圆点，但无设局→收局连线、颜色非语义 |

### 4.2 缺失与坑

1. **大纲粒度 = 卷**：`books/book_002/storyline.json` 的 5 条 outline 跨 1-150 章（开局 1-20 / 布局期 21-55 / 碾压期 56-95 / 跨界 96-125 / 最终清算 126-150，全部 `stages:[]`）——是「篇/卷」不是「弧」。
2. **没有「弧」中间层**：大纲库只有 书(StructureTemplate) → 卷级阶段(StageNode, 25-100 章) → 场景(PlotTemplate) 三层；`StageNode.key_events`（`libraries/structure.py:16`）本是 mini-大纲原料，却只被当桥段匹配上下文（`libraries/outline_generator.py:839-840`），从未被提升成弧。
3. **线程单归属**：一个桥段只有一个 `thread_id`（`libraries/storyline.py:249`），不能同时属主线+副线（现实中一个章节常同时推两条线）。
4. **narrative 存而不用**：不进写作流，`narrative_target` 只存不渲染（`story_line.js:74` 后无消费）。
5. **无并行 POV**。
6. **存量数据坑**：book_002 的 `threads` 条目缺 `id` 字段（实测 `id=None`），而前端 `story_line.js:120` 用 `t.id` 做键 → 线程匹配会失效；book_001 的 outline/plot 的 `id` 全空。当前「线程 id 对齐」约定与数据不一致。

## 五、「大纲变卷」根因（为什么 agent 会产出卷一/卷二）

按因果链梳理：

1. **库粒度缺弧层**：`StructureTemplate`（书级，total_chapters=150-500）→ `StageNode`（卷级，`min_chapters/max_chapters` 25-100，如 `libraries/structure.py:112-154` 玄幻 500 章分 8 阶段）→ `PlotTemplate`（场景级 1-6k 字）。中间**没有约 10 章级的弧**，任何生成只能落到「卷」或「场景」两档。
2. **「卷」字样的直接来源**：`libraries/data/structures.jsonl` 里 scout 入库模板的 stages 硬编码成 `['第一卷·凡尘起点弧','第二卷·机缘初现弧',…]`；源头是 `plugins/fanqie_scout.py:641-643` 入库 prompt 要求「卷(Volume)→弧(Arc)→关键事件」三级，却把卷+弧**压扁**进 `stages[].name`。
3. **agent 把模板的 stage 提升成 outline**：agent 挑中 `struct_chuanyue_01` 后，把它的 5 个 stage 名（开局/布局期/碾压期/跨界/最终清算）直接做成 5 条 outline 的名字前缀（book_002 实测），于是每条 outline = 一条卷。book_001 更糟：5 条 outline 的 `start/end` 全是 1-30（重叠/并列）。
4. **契约与描述默认「大纲=卷」**：`agent_tools.py:1096` set_outline 描述写「`order` 卷内序号」，`NOVEL_AGENT.md:44` 同——从数据结构到 MCP 描述一路把大纲当卷，没有 prompt 引导「大纲 = 情节弧」。

**一句话**：库没有「弧」层 + agent 把「卷级 stage」提升成「大纲」 + 契约默认大纲=卷 → 大纲长成卷一/卷二。

## 六、末日文例子落地（示范：把概念映射到数据）

一本书《XX》——末日题材，用现有 `OutlineSlot` / `PlotSlot` / `threads` 表达：

```
大纲弧 arc_1「末日来临前囤物资」  第 1-10 章    ← 方向：在期限前攒够资源
├─ 桥段 p1「发现末日征兆」          主线
├─ 桥段 p2「疯狂采购 + 抢购冲突」    主线        （与 p1 构成囤积主线的前两拍）
├─ 桥段 p3「金手指变现补库存」      主线
└─ 桥段 p4「最后一批物资入仓」      主线        （弧 1 收尾：方向达成）

大纲弧 arc_2「末日爆发 · 生存重建」  第 11-30 章  ← 方向：活下来并重建秩序
└─ 桥段 p5「收局：末日源头阴谋揭晓」 伏笔线      （resolves_plot_id = 设局桥段 sX，设在弧 1 第 8 章）

线程：
  主线   = 囤积求生 + 生存重建（p1-p5 中主线部分）
  副线   = 家人/女友对主角「疯狂囤货」的怀疑与和解（散布在弧 1、弧 2）
  伏笔线 = 末日源头阴谋（设局 sX 第 8 章 → 推进 → 收局 p5 第 28 章）
```

**插叙**：写作顺序经 `_threaded_ordered_plots` 变成「主线囤积 2 步 → 副线 1 步 → 伏笔 1 步」轮流，即 A（囤积）开头 → B（阴谋/副线）再开头 → 各自收尾。
**并行视角（若未来支持）**：弧 1 同一时间窗内，主角视角「抢购囤货」与 政府视角「封城管制」两条 POV 线并排渲染。

## 七、建议的数据模型演进（供后续决策，**本次未实施**）

方向与现状的差距，按优先级排列：

1. **大纲 = 弧**（改 `OutlineSlot` 粒度语义）
   - `OutlineSlot` 默认 `start/end` 跨度改为 5-15 章（情节弧），卷降为**可选上层容器**（书→卷→弧→桥段）或保持扁平弧列表 + 新增 `parent_arc_id` 支持弧套子弧。
   - 涉及：`libraries/storyline.py`（OutlineSlot 字段 + `to_dict`/`from_dict` 同步）、生成逻辑与 prompt、`NOVEL_AGENT.md`/`agent_tools.py` set_outline 契约（把「卷内序号」改「弧内序号」）、`story_line.js` 渲染。
2. **弧层提升**
   - 把 `StageNode.key_events`（`structure.py:16`）或 `stages` 明确为**子弧/桥段**，而不是「卷内阶段」；`structure_to_stages`（`libraries/storyline.py:399-406`）目前丢掉了 `description` 和 `foreshadow_opportunities`，应保留。
3. **线程多归属**
   - `thread_id` → `thread_ids: list`，一个桥段可同时推主线+副线；UI 线程泳道加强（设局→收局加连线，`story_line.js:358-389` 的 SVG 连线逻辑可复用）。
4. **narrative 进写作流**
   - 倒叙/插叙改变桥段写作顺序或注入 prompt；`narrative_target` 渲染到 UI。
5. **并行 POV（可选扩展）**
   - 桥段加 `pov` 字段；写作允许同时间窗切视角；UI 同时间窗双泳道并排。
6. **修存量数据**
   - book_002 `threads` 补 `id`、book_001 outline/plot 补 `id`（或迁移脚本）。

**最小改动面**：`libraries/storyline.py`（OutlineSlot/PlotSlot 字段 + 序列化）+ `libraries/structure.py`（弧层模板）+ 生成 prompt + `story_line.js`（可视化）。

## 九、术语表

| 术语 | 含义 |
|---|---|
| 大纲（情节弧 Arc） | 掌控方向的叙事段，约 5-15 章；含起承转合；可套子弧 |
| 桥段（Plot Beat） | 弧内的戏剧节拍/事件/场景，约 0.3-2 章；可套子桥段 |
| 线程（Thread） | 横向贯穿全书的一条叙事线索（主线/副线/伏笔线），由跨弧的桥段组成 |
| 设局 / 收局 | 一条线索的「埋钩子」（resolves_plot_id 为空）与「兑现」（resolves_plot_id 指向设局桥段） |
| 插叙（interleaved） | 多线程交错推进；当前由 `_threaded_ordered_plots` 实现于写作顺序，UI 仅上色 |
| 并行视角（POV） | 同一时间窗内多条视角线并排呈现；当前未实现 |
| 卷（Volume） | 比弧大的可选分组（多个弧）；当前 `OutlineSlot` 实际落成了卷级 |

## 十、豆包研究对照与收敛模型

> 本节对照另一 AI（豆包）的 `docs/豆包研究结论.md`《故事生成系统：故事线、大纲、桥段、叙事线程的关系研究》。**结论：两篇核心一致；豆包多拆出「故事线（内容层）」「叙事线程（调度层）」两个概念，正好解开你对「线程」的困惑。**

### 10.1 两篇对照

**共同点（两篇一致，可收敛）**：

| 结论 | 豆包 | 本研究 |
|---|---|---|
| 大纲 ≠ 卷，卷是输出格式/分组 | 「卷、章节是输出后处理产物，不是素材层定义。绝不允许大纲节点直接等价为卷」 | 「大纲=情节弧，卷比弧大得多」 |
| 大纲 = 目标/方向节点，桥段 = 可执行剧情片段 | 「大纲是骨架目标，桥段是血肉」 | 同（§2.1） |
| 大纲应树状嵌套，缺子层 = 「大纲变卷」根因 | 「扁平列表非树，缺中间子大纲」 | 「库粒度缺弧层」 |
| 线程 ≠ 大纲/桥段 | 「两层概念混在一起」 | 「三正交维度」 |
| 插叙/并行 = 改调度不改素材 | 「素材不动，只改调度策略」 | 「核心机制代码已支持」 |

**关键差异（豆包新贡献）**：
1. **豆包把「线程」拆成两个概念**：
   - **故事线（内容素材层）** = 一条因果链，**拥有自己的大纲树 + 桥段池**（例：主角求生线 / 邻居一家命运线），属于素材；
   - **叙事线程（调度层）** = 执行器，负责「启动桥段 → 挂起存断点 → 切走 → 回来续写」，决定输出顺序。
   
   → 本研究原 §2.2 把「主线/副线/伏笔线」称为「线程」（横向内容线），而把调度机制（`_threaded_ordered_plots`，`libraries/storyline_writer.py:169-206`）当作既有实现没提升为一等概念。**现有代码里的 `thread_id` 同时承载「内容线」与「隐式调度依据」两层职责**——这正是「线程含义跟大纲桥段很像」困惑的根源。
2. **故事线拥有独立大纲树**：本研究模型里大纲全书共享、桥段挂一条弧+一条线程；豆包主张每条故事线各有一套大纲树+桥段池（更能表达「主角线/邻居线各自推进」）。
3. **卷彻底移出素材层**：豆包主张卷 = 纯后处理分组（取代本研究原 §七「卷作可选容器」建议）。
4. **断点挂起上下文**：豆包强调叙事线程保存「写到一半的桥段断点 + 人物状态」，支持桥段写一半挂起切走再回来续写；现有代码以整桥段为单位、`written_chapter`（`libraries/storyline.py:246`）记进度，**没有显式挂起/恢复上下文**——这是插叙体验的真正缺口。

**小分歧**：豆包「桥段不嵌套桥段」（内部可有微型大纲）；现有代码有 `parent_plot_id` 链式嵌套（`libraries/storyline.py:230-231`，无真实数据用）。需后续定夺。

### 10.2 收敛模型（合并后）

```
作品
├─【内容素材层】
│  ├─ 大纲（树状目标节点，可嵌套；大目标拆子目标；挂载桥段 ID 列表）
│  ├─ 桥段（可执行剧情片段，挂在大纲节点下；可含微型子大纲）
│  └─ 故事线（因果链 = 自己的大纲树 + 桥段池；主线/副线/伏笔线各一；自带视角 POV）
└─【调度层】叙事线程调度器
   ├─ 调度策略：顺叙 / 交替并行（崩铁式）/ 交叉插叙
   ├─ 维护挂起桥段的断点上下文（写作进度 + 人物状态）
   └─ 输出桥段序列 → 后处理：按字数分组 → 章节 / 卷（卷≠素材）
```

**一句话**：豆包多拆出的「故事线（内容）」「叙事线程（调度）」两层，正是解开「线程困惑」的关键——内容线与调度器不该共用同一个名字。

### 10.3 收敛模型 vs 现有代码（差距清单）

| 现状 | 收敛目标 | 位置 |
|---|---|---|
| `thread_id`（主线/副线/伏笔线）被当「线程」 | 语义重定位为「**故事线**」（storyline_id）；每条故事线应有自己的大纲树（现大纲全书共享、扁平） | `libraries/storyline.py:249`、`outline_generator.py:1064-1073` |
| `_threaded_ordered_plots`（2:1 加权轮询） | = **叙事线程调度器雏形**，升级：断点挂起/恢复上下文、可配置调度模式 | `libraries/storyline_writer.py:169-206` |
| `OutlineSlot` 扁平卷级（book_002 跨 1-150 章） | 树嵌套（`parent_arc_id`）+ 粒度改弧级 | `libraries/storyline.py:198-217` |
| 卷在 `OutlineSlot` 里 | **移出素材层**，改后处理分组 | `books/book_002/storyline.json` |
| 无 POV 概念（写作锁定主角视角） | 视角挂**故事线**上 | `libraries/storyline_writer.py:37` |
| 整桥段写作 + `written_chapter` 记进度 | 叙事线程加**断点上下文**（写作进度 + 人物状态） | `libraries/storyline_writer.py:549-656` |

**对原 §七「建议的数据模型演进」的取代关系**：
- 取代：卷作可选容器 → **卷移出素材层（后处理）**；线程多归属 `thread_ids` → **改故事线语义**；桥段加 `pov` 字段 → **视角挂故事线**。
- 保留：大纲粒度改弧级（§七.1）、`key_events` 提升为子弧（§七.2）、narrative 进写作流（§七.4）。

### 10.4 结论

两条独立研究（本研究 + 豆包）一致确认：**大纲 ≠ 卷、大纲 = 树状目标节点、桥段 = 可执行片段、插叙/并行靠调度不改素材**。豆包的「故事线（内容）/叙事线程（调度）」分层是概念清晰化的关键下一步——建议作为后续数据模型演进（§七）的框架底座。

## 附录 A：术语表（增补）

| 术语 | 含义 |
|---|---|
| 故事线（Storyline） | 内容素材层的一条因果链，拥有自己的大纲树 + 桥段池；主线/副线/伏笔线各一条；自带视角 |

| 断点上下文 | 叙事线程为「写到一半的桥段」保存的写作进度 + 人物状态，供切走后再回来续写 |
